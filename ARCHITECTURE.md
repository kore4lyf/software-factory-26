# Architecture: one factory, two planes

There is one software factory. It has two planes, and this document is the seam between them. They are not two products that might be joined up later. They are two halves of one system, and the harness is the part that carries the method.

## The two planes

| | Harness plane | Host plane |
|---|---|---|
| **What it is** | the method: 14 skills, 10 role briefs, the scope as a work queue, the loop | the machinery: triggers, worker sandboxes, secrets, git, the pull request |
| **Where it lives** | `skills/`, `references/`, `harness/` | generated by `sf-create-factory`: a factory repo, `src/`, `factory.config.json` |
| **Where it runs** | inside the agent, wherever the agent runs | GitHub Actions runner, plus one sandbox per worker |
| **What it owns** | decisions, specs, code, evidence | intake, scheduling, credentials, commits, the PR |
| **Who starts it** | the host, once per issue | a `ready` label |

## The three seams

### 1. `repo.setup` installs the harness

The harness is not shipped by the host. It installs through the same `npx skills add` command a human uses, so the worker and the engineer run byte-identical skills. `repo.setup` already runs arbitrary commands in the sandbox before the agent starts, so this needs no code:

```json
"setup": [
  "npm ci",
  "npx --yes skills@latest add <factory-repo-url> --skill '*' -g -a claude -y"
]
```

### 2. `jobFiles` carries the entry point

`harness/AGENTS.md` lands at `$HOME/AGENTS.md` in the sandbox. Job files are read fresh on every job, so editing the harness takes effect on the next run with no image rebuild. The reference files land beside the skills at `$HOME/.agents/references/`.

### 3. The prompt invokes the method

`run.mjs` reads an optional `harness` block in `factory.config.json`. Present, the prompt tells the agent to load `sf-factory-run` and follow it. Absent, the agent is a plain coding agent, which is exactly how the template behaved before. The block is optional and backward compatible on purpose: the host's implementation is proven and this changes nothing unless a factory asks for it.

**The precedence is already right.** The host's prompt has always said its rules win over "any other instructions you have been given, including house rules files", so the harness outranks the app repo's own `AGENTS.md` without any new work.

## One vocabulary

The two planes already describe the same thing in different words. This is the mapping, and it is the reason they are one factory rather than two.

| Host concept | Harness concept | Same thing? |
|---|---|---|
| issue with the `ready` label | intake, the start of the scope | yes |
| issue title, body, comments | the engineer's words, the input to `/sf-scope` | yes |
| one run, one branch | one run, one feature cycle | yes |
| `factory:running` | a run in flight | yes |
| `factory:review` | checks passed, waiting for a human | yes |
| `factory:needs-attention` | `blocked`, and only ever for a human reason | yes |
| `repo.checks` | the verify station | yes |
| the agent's summary | the run report | yes |
| the pull request | the per change scope | yes |
| the worker Box | isolated context for one feature | yes |
| `jobFiles` | the harness delivery | yes |

So an issue is one feature. The worker runs the harness's per feature cycle and hands back a pull request that carries the code, the spec it was built to, and the evidence it was verified against. That is a better pull request than a diff and a paragraph, and it comes free from the vocabulary lining up.

## What each plane must never do

| The harness must never | The host must never |
|---|---|
| commit, push, or touch git, inside a worker | let an agent hold a token, or decide a deploy |
| provision infrastructure | decide what to build, or how |
| ask a question mid job | rewrite the app repo's rules to suit itself |
| write inside a skill folder | pin the harness, so the two drift |

That last row is the one most worth defending. The host deliberately does not pin a harness version, because a pinned harness is a second copy of the method and the whole point is that there is one. When the harness changes, every worker runs the new one on its next job.

## Generating the config

`scripts/emit-harness-config.mjs` reads this repo and prints the `setup` command and the `jobFiles` array, so the host's config is generated from what is actually on disk. Adding a skill or a reference file cannot leave a host pointing at something that no longer exists.

```bash
node scripts/emit-harness-config.mjs --source https://github.com/OWNER/software-factory-26
```

## What the harness is still missing

Named honestly, so it is not rediscovered as a surprise:

- **Continuous feedback.** Monitoring produces signals and signals become the next issue, today by a human adding a label. Nothing watches production and opens an issue on its own.
- **Spend metering.** A skill cannot see token billing. The host can report run counts and worker minutes, which is a proxy and not money.
- **Model routing enforcement.** The host stores model and effort per Box, which is real. The harness recommends a tier per role and records what it actually used, which is the part it cannot guarantee.
