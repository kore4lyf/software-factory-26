# Software Factory 26

An installable software factory. Fourteen skills that take an idea or a GitHub issue to shipped, verified, documented code, with an orchestrator that delegates the work to sub-agents instead of doing it inline.

Everything the factory writes goes to files in your repo. A session can end, a session can be cleared, and the work is still there because it was never trapped in a conversation.

> **Thirteen of the fourteen skills are markdown and dependency-free scripts that read and write your project. One is not.** `sf-create-factory` builds a host that runs coding agents unattended, with permission prompts disabled and credentials on a worker's disk. That is what it is for, and it is opt-in. **Read [SECURITY.md](SECURITY.md) before you run it.**

## What this is

One factory with two halves. They are not two products that might be joined up later.

| | The harness | The host |
|---|---|---|
| **Is** | the method: 14 skills, 11 role briefs, the scope as a work queue, tier gates, commit checkpoints | the machinery: GitHub Actions triggers, worker sandboxes, secrets, git, the pull request |
| **Lives in** | `skills/`, `references/`, `harness/` | generated by `/sf-create-factory`: a factory repo, `src/`, `factory.config.json` |
| **Owns** | decisions, specs, code, evidence | intake, scheduling, credentials, commits, the PR |

An issue is one feature. A worker runs the harness's per feature cycle and hands back a pull request carrying the code, the spec it was built to, and the evidence it was verified against.

Full detail in [ARCHITECTURE.md](ARCHITECTURE.md).

## Install

The skills ship as installable Agent Skills and nothing runs until you install them.

```bash
npx skills add kore4lyf/software-factory-26
```

That is the whole install. It detects your agent, installs all 14, and asks before writing anything.

To be explicit about scope and agent:

```bash
# Globally, so the factory works in every project on your machine
npx skills add kore4lyf/software-factory-26 -g -a opencode -y

# Into just this project, committed so the team gets them too
npx skills add kore4lyf/software-factory-26 -a opencode -y

# Look before you leap
npx skills add kore4lyf/software-factory-26 --list

# Just one skill
npx skills add kore4lyf/software-factory-26 --skill sf-factory-run
```

Working on the factory itself, from a clone:

```bash
git clone https://github.com/kore4lyf/software-factory-26
cd software-factory-26
npx skills add . -g -a opencode -y
```

Verify, and confirm nothing was written into a skill folder:

```bash
ls ~/.agents/skills | grep sf-     # 14 skills
npm run check:write-rule            # the write rule holds
```

The installer creates a **copy**, not a symlink, because Windows falls back to copying without Developer Mode. So after you edit a skill in the repo, reinstall to pick the change up. It takes ten seconds and the stale copy is silent.

Two things worth knowing. The `sf-` prefix is deliberate, so these skills never collide with same named skills already on your machine. And `skills/` is deliberately flat, one directory per skill, because the installer's catalog layout is unreliable.

For a worker sandbox you will need more than one agent, and the ids are not guessable, `claude-code` not `claude`:

```bash
npx skills add kore4lyf/software-factory-26 -g -a opencode -a claude-code -a codex -y
```

## Three ways to use it

### 1. A whole product, you drive

The factory runs itself end to end and does not stop to ask.

```
/sf-factory-run
```

Pick a mode at the start:

- **`auto-recommended`** (default). The architect takes its own recommended option for every decision, writes it into the spec, and tags it for you to review at the end. Nobody is interrupted.
- **`I decide upfront`.** Every load bearing question across every feature is collected into one batch panel, you answer once, then the build never asks again.

You get a whole runnable product plus `factory/runs/<run-id>.md` with its assumptions, absorbed blockers and follow ups.

### 2. An issue at a time, the factory drives

Set up once with `/sf-create-factory`, which builds a host: GitHub Actions triggers, a pool of worker sandboxes, a label state machine, and the harness installed into every worker.

```
label an issue `ready`  →  a worker claims it  →  the harness runs the feature cycle  →  a pull request
```

Labels show the state: `ready`, `factory:running`, `factory:review`, `factory:needs-attention`.

Generate the config fragments from this repo so the two halves cannot drift:

```bash
npm run emit:harness-config -- --source https://github.com/OWNER/software-factory-26
```

### 3. Single skills, you supervise

Nothing forces the whole loop. Run the stations your change needs.

| You want | Run |
|---|---|
| a plan of what to build | `/sf-scope` |
| context files the other skills read | `/sf-audit` |
| a decision written down before code | `/sf-architect` |
| code from a spec | `/sf-develop` |
| proof it actually runs | `/sf-check verify` |
| a second opinion from another model | `/sf-check review` |
| tests that keep it working | `/sf-test` |
| production | `/sf-deploy-app` |
| the root cause of a bug | `/sf-debug` |
| the write up | `/sf-document` |
| docs back in line with code | `/sf-sync` |

Nothing is a track you are locked onto. A bug goes straight to `/sf-debug` with no scope or spec needed. `/sf-scope` with no argument is a status read, not a step.

## The loop

The loop is three nested scopes plus one interrupt, not a pipeline. Confusing them is the most common way to get it wrong.

| Scope | Runs | Skills, in order |
|---|---|---|
| Per project, once | before anything reads the codebase | `sf-audit` then `sf-scope` |
| Per feature, in scope order | all the way through | `sf-architect` → `sf-develop` → `sf-check verify` (Alpha+) → `sf-test` (Beta+) → `sf-check review` (GA) → `sf-document` (GA) |
| Per change, around merge | once the branch is done | `sf-check review` → `sf-document` → `sf-deploy-app` (GA) → `sf-sync` |
| Anytime, on failure | no row, no box | `sf-debug` |

**The scope is the work queue.** You never remember what comes next, the agent reads it. Each feature row carries boxes, and the first unticked box is the instruction: `Design it` unticked means architect, `Build it` unticked means develop.

The **workflow tier** decides which closing boxes exist on a row at all, so at Prototype there is no `Verify it` box and nothing to check:

| Tier | Required |
|---|---|
| Prototype | `sf-develop` only |
| Alpha | adds `sf-check verify` |
| Beta | adds `sf-test` |
| GA | adds `sf-check review` and `sf-document` |

A **verified feature is a rollback point.** The orchestrator commits the tree once a feature's checks pass and records the SHA in the run file, before the next build starts. Developing the next feature without one leaves no way back to the last state anyone proved worked. Checkpoints do not run inside a sandbox, where the host holds the credentials and does the git work itself.

## What lands in your project

Everything the factory writes about your project goes to `factory/` at the project root, never to `docs/` and never into a skill folder.

```
factory/
  scope/          what to build, in order, with decision seeds
  specs/          build specs, the contracts a build follows
  reviews/        verify and review findings
  runs/           one file per run: state, checkpoints, follow ups
  deploy-ledger.md   deploy and rollback events
  releases/  postmortems/
```

It is a dedicated folder, so there is no docs site detection and no alternative base. See [factory/README.md](factory/README.md).

## Commands

| Command | Runs where | What it does |
|---|---|---|
| `npx skills add kore4lyf/software-factory-26 --list` | anywhere | What is available to install |
| `npm run check:write-rule` | the factory repo | Proves nothing was written inside an installed skill folder |
| `npm run telemetry` | the factory repo | Cycle time, both spans, and which half is the constraint |
| `npm run emit:harness-config` | the factory repo | Prints the host config fragments, generated from this repo |

The first works from any directory. The other three are scripts that live in this repository, so they only make sense from a clone of it, which is why `npm run check` is the command to reach for before contributing.

Telemetry reads `specced_at`, `built_at` and `verified_at`, which three different skills already write. It is deterministic, so it costs no tokens and always gives the same answer.

## The 14 skills

| Skill | Owns |
|---|---|
| `/sf-scope` | `factory/scope/`. Turns an idea into an ordered plan, deliberately shallow so decisions stay open |
| `/sf-audit` | `AGENTS.md` everywhere. Writes the context every later skill reads |
| `/sf-architect` | `factory/specs/` content and status. Makes the decision before code exists |
| `/sf-develop` | App code. Builds from a spec, runs migrations, advances the scope |
| `/sf-check` | `factory/reviews/`. `verify` drives the real app, `review` reads the diff on another model |
| `/sf-test` | Your test dirs. Normal path, edge cases, error states, accessibility |
| `/sf-start-app` | Scaffolds a working full stack app from an interview |
| `/sf-review-app` | Reports on an existing app: security, discoverability, drift |
| `/sf-deploy-app` | `factory/deploy-ledger.md`. Production, with a gate and automatic rollback |
| `/sf-create-factory` | Builds the host: triggers, workers, the harness in every sandbox |
| `/sf-factory-run` | The orchestrator. Reads, decides, dispatches, records. Never writes code |
| `/sf-debug` | The smallest fix that works, plus a regression test handed to `/sf-test` |
| `/sf-document` | `CHANGELOG.md`, release notes, postmortems, PR bodies |
| `/sf-sync` | Surgical edits to `AGENTS.md`, scope rows and spec status lines |

## Where the rules live

**Agents read `SKILL.md`, not this file.** Anything an agent must obey lives in a `SKILL.md` or in one of the briefs under `skills/sf-factory-run/agents/`. If you are looking for a rule, it is not here.

- [AGENTS.md](AGENTS.md) — the conventions, the write rule, the orchestration rules
- `skills/<name>/SKILL.md` — how each skill behaves
- `skills/sf-factory-run/agents/orchestrator.md` — **read this first** if you are orchestrating. It teaches the loop
- `harness/AGENTS.md` — the entry point that lands in a worker sandbox
- `.opencode/plugins/factory-guard.js` — a gate that throws if anything tries to write into a skill folder
